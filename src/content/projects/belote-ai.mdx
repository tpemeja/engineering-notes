## Overview

The French trick-taking card game Belote is implemented as
a proper [OpenSpiel](https://github.com/google-deepmind/open_spiel) game
(chance-based dealing, imperfect information enforced by the framework, a
flat action space covering bidding and card play). 

Every agent built on top of it, from uniform random up to a PyTorch value 
network are compared against the others through a seeded, confidence-interval-backed 
evaluation harness rather than a handful of "it felt stronger" test games. 

A longer-term goal is bringing LLMs into that same comparison, not just to see
how they rank against other agents, but whether they can actually pull off Belote's 
tactical plays, like an *appel* (calling for a suit via a discard signal) or an 
*impasse* (a betting on where a specific card sits).

## Problem

Belote didn't exist as an OpenSpiel game, but the harder problem was proving
that any agent built for it was actually better than the last one :

- **No existing implementation.** Belote has no OpenSpiel game to build or
  benchmark agents against in the first place.
- **Evaluation noise compounds with imperfect information.** Small-sample
  results can look like real improvements until the sample size grows, and
  Belote's chance-based dealing and hidden hands push variance up further.
  So a *trustworthy* comparison needs enough seeded deals to be genuinely
  expensive to run.
- **Win rate alone won't reveal *how* an LLM plays.** Comparing an LLM against
  the other agents isn't just about who wins, it's whether the LLM can
  execute known tactical plays like an *appel* or an *impasse* at all, which
  an aggregate points margin can't show. That needs per-decision scoring
  against known-good tactical baselines, and LLM calls are too slow and
  expensive to lean on thousands of simulated deals per comparison the way
  ISMCTS or a value network can.

Any one of these is manageable alone, but together they mean win rate over a 
batch of games isn't enough. It needs a real implementation to run games on, 
enough seeded samples to separate skill from noise, and a way to score 
individual decisions for agents (such as an LLM) or human players, 
who can't realistically be evaluated over thousands of deals. 
That's why the evaluation harness became the first deliverable rather than 
an afterthought bolted on once agents existed.

### Game Implementation |#game-implementation|

Belote is not part of the supported games in `OpenSpiel`. So the first part of the project is to
fork OpenSpiel and add a Belote implementation to it, well-tested, optimized, and documented
enough to eventually open a pull request back upstream. As I am more confident in Python, I
start there, planning to convert it to C++ later.

---

To implement the game in `OpenSpiel`, two objects need to be defined: 
- `Game`, which is relatively simple and only contains the parameters of the game.
- `State`, which contains all the game logic, including how the game is organized, the rules, and the scoring.

### Simulation Harness |#simulation-harness|

<PhaseJournal projectSlug="belote-ai" phaseId="simulation-harness" />

Before writing any real agent, the harness itself needed proving: two
`pyspiel` uniform-random bots played against each other over seeded deals,
with the statistical machinery every later comparison depends on (paired
matches, confidence intervals, sample sizing) built and validated here
first instead of reinvented per phase.

---

A fixed dealer gives one team a permanent bidding-order advantage that would
otherwise be indistinguishable from a real skill difference. The fix borrows
duplicate bridge's trick: play the identical seed twice, dealer rotated one
seat, and average the two margins.

<DecisionTable
  decisions={[
    {
      label: 'Match design',
      chose: 'Dealer-mirrored (paired) deals',
      insteadOf: 'A single fixed-dealer match',

    },

For this random-vs-random run, the 300-deal pilot measured a paired stdev
of ~66.6 points/deal, which the power formula turned into a target of 1,393
paired deals (to detect a ±5 pt/deal effect at 80% power, 95% confidence).
Running that many gave a paired margin of **-1.15 pts/deal, 95% CI
[-4.47, +2.17]**, an interval straddling zero, with an achieved half-width
(±3.32) inside the ±5 target. Two identical uniform-random bots showing no
detectable edge is exactly the result the harness needed to produce before
being trusted on anything else.

<ConfidenceIntervalChart
  unit="pts/deal"
  metrics={[
    { label: 'Dealer 0 only', mean: 13.58, ciLower: 7.07, ciUpper: 20.08 },
    { label: 'Dealer 1 only', mean: -15.87, ciLower: -22.44, ciUpper: -9.31 },
    {
      label: 'Paired (seat-order cancelled)',
      mean: -1.15,
      ciLower: -4.47,
      ciUpper: 2.17,
      highlight: true,
    },
  ]}
/>

The two single-dealer arms each look "significant" on their own (95% CIs
excluding zero), but in opposite directions and of similar size, exactly
the seat-order artifact the pairing exists to cancel, not a real skill gap
between identical bots. Only the paired arm (highlighted) straddles zero,
which is the correct answer.

<WinTieLossBar
  team0Label="Team 0 (Random)"
  team1Label="Team 1 (Random)"
  rows={[
    { label: 'Dealer 0 only', team0: 0.477, tie: 0.0, team1: 0.523 },
    { label: 'Dealer 1 only', team0: 0.518, tie: 0.0, team1: 0.482 },
    {
      label: 'Paired (seat-order cancelled)',
      team0: 0.404,
      tie: 0.153,
      team1: 0.443,
      highlight: true,
    },
  ]}
/>

Both single-dealer rows show 0% ties because one deal can never land on an
exact 0 margin. A made contract splits the points as actually won (say 90
vs 72); a failed one sweeps everything to the defenders instead. Either way
it's never perfectly even, since an 81-81 result is scored as a failed
contract rather than a tie.

The paired row's 15.3% is a different kind of tie: not one deal ending
even, but two mirrored deals landing on equal and opposite margins (Team 0
wins by X with dealer=0, Team 1 wins by that same X with dealer=1), which
average out to exactly 0. It's reported as its own outcome rather than
folded into the win-rate denominator, since it genuinely means neither team
had a net edge across both plays.

---

<Callout variant="lesson" title="A measurement tool has to prove it reports zero first">
  Two identical uniform-random bots should show a paired margin
  statistically indistinguishable from zero. That's not a throwaway smoke
  test, it's the calibration check the whole evaluation harness has to pass
  before any later "this agent is stronger" claim is allowed to rest on it.
</Callout>

### RuleValidBot |#rulevalidbot|

<PhaseJournal projectSlug="belote-ai" phaseId="rulevalidbot" />

The first real agent, deliberately minimal: the goal was reliably beating
the random baseline with a tight confidence interval, not playing well.

  nodes={[
    {
      name: 'RuleValidBot',
      fields: [
        {
          name: 'bid1 / bid2',
          detail: "take, or name the strongest suit, if the hand's trump-adjusted points are >= 31; otherwise pass",

        { name: 'play', detail: 'play the highest point-value legal card' },

Against uniform random, N sized by the same pilot-then-size procedure the
walking skeleton built (a 300-deal pilot measured stdev, which solved for
N=1,250 paired deals to detect a ±5 pt/deal effect at 80% power):

<WinTieLossBar
  team0Label="RuleValidBot"
  team1Label="Random"
  rows={[{ label: 'RuleValidBot vs Random', team0: 0.571, tie: 0.067, team1: 0.362, highlight: true }]}
/>

<ConfidenceIntervalChart
  unit="pts/deal"
  metrics={[{ label: 'RuleValidBot vs Random', mean: 15.93, ciLower: 12.19, ciUpper: 19.67, highlight: true }]}

Raw win rate and mean margin can disagree without contradicting each other.
Belote's all-or-nothing contract makes a loss a fixed, capped swing (fail
the contract and the other team sweeps 162), while a win's size is
uncapped, so a policy whose wins are bigger than its losses can win on
average while still losing more individual deals than it wins.

<Callout variant="info">
  Not charted above since only the paired result is shown, but the
  dealer=0-only arm behind this same result is exactly that case:
  RuleValidBot loses that raw count 45.1% to 54.9%, yet still averages
  +21.48 pts/deal on it.
</Callout>

Splitting *how often* a team gets to declare from *how well it does when it
does* told a more precise story than the headline number alone:

<PercentBars
  title="Declare frequency"
  bars={[
    { label: 'RuleValidBot declares', value: 0.303 },
    { label: 'Random declares', value: 0.697, highlight: true },
  ]}
/>
<PercentBars
  title="Declare success rate"
  bars={[
    { label: 'RuleValidBot succeeds', value: 0.708, highlight: true },
    { label: 'Random succeeds', value: 0.630 },

/>

Random gets to attempt a contract more than twice as often (its bidding is
a blind coin flip that regularly preempts RuleValidBot before it even gets
a turn), yet still succeeds less often when it does. Raw win rate would
have conflated those two effects; reporting them separately keeps the real
skill signal (70.8% vs 63.0% success) from hiding behind the opportunity
imbalance (30.3% vs 69.7% frequency), and vice versa.

That's not the same as showing "be more selective" is the right strategy,
though. RuleValidBot has no way to know in advance whether a given hand
will actually succeed, it only estimates via the trump-adjusted points
heuristic, and being pickier mechanically raises the success rate just by
filtering for stronger hands, at the cost of giving up most opportunities
entirely. Whether a given threshold trades away too much frequency for
that higher per-attempt rate is exactly what the sweep below tests.

The `>= 31` take-threshold and "always play highest-value card" were both
unexamined choices, so the natural next question was whether 31 was even a
good number. A sweep from 30 to 80, evaluated against the same fixed random
reference at each point (5,000 paired deals per threshold), answered that
directly:

Margin and win rate climb steeply from threshold 30 up to about 43, then
plateau from there on. Threshold 58 is the nominal best on both
metrics (+31.36 pts/deal, 69.9% win rate), but it isn't meaningfully
distinguishable from most of the 40s and 50s, every point's CI in the
plateau overlaps its neighbors. The real finding is "stop being reckless
past ~43," not "58 is the answer."

Splitting *how often* RuleValidBot declares from *how well it does when it
declares vs. defends* explains *why* the plateau happens, not just that it
does:

<SweepChart
  series={sweepBreakdownSeries}
  xDomain={[29, 81]}
  yDomain={[0, 1]}
  xTicks={[30, 40, 50, 60, 70, 80]}
  yTicks={[0, 0.2, 0.4, 0.6, 0.8, 1]}

RuleValidBot's hand-points threshold has a real ceiling: a 5-card hand
can't score above roughly 66, so past that it never declares at all, and
its declare rate is already under 5% by the mid-40s. Its win rate *when it
does declare* keeps climbing as the threshold rises, past 90% at the high
end, though noisy there (the widening band) since only a handful of hands
ever qualify. Its win rate *when defending*, on the other hand, barely
moves: flat around 42% regardless of threshold, since that side depends
only on how often Random's own blind bid fails, not on anything
RuleValidBot decides.

<Callout variant="lesson" title="A paired win rate isn't the same statistic as the per-deal rate behind it">
  Past threshold ~67, RuleValidBot never declares, so every deal is decided
  purely by whether Random's contract succeeds, and win rate when defending
  sits at 42.2%. Naively, the overall paired win rate should land near
  there too. It doesn't, it's 69.6%, confirmed directly by rerunning 3,000
  deals at a threshold well past that ceiling and inspecting the raw
  margins. Cause: Belote's
  all-or-nothing contract makes wins and losses wildly asymmetric in size
  (a rare failed-random-contract win averages +166.6, a common
  successful-random-contract loss averages only -69.3), and averaging two
  draws from a distribution shaped like that pushes the paired split well
  past what the raw per-deal split alone would suggest. A paired win rate
  and a per-deal win rate are genuinely different statistics, not two views
  of the same number.
</Callout>

<Callout variant="lesson" title="A parameter tuned against one opponent doesn't automatically transfer">
  The sweep holds everything fixed and evaluates each threshold against a
  *fixed* reference (random), the same principle chess engines use for SPSA
  tuning against a fixed reference engine, deliberately not another
  RuleValidBot threshold, so the scale doesn't shift as candidates change.
  That's the right way to find "better against random," but a threshold
  climbing purely by capitalizing on random's careless contract failures
  isn't necessarily better against a less careless opponent later.
  Confirmed later, not just a hedge: the next phase's partner-aware
  card-play strategy found exactly that, a threshold tuned against random
  didn't automatically carry over once the opponent got smarter.
</Callout>

### ISMCTS |#ismcts|

<PhaseJournal projectSlug="belote-ai" phaseId="ismcts" />

OpenSpiel's information-set MCTS, which required implementing
`resample_from_infostate` on `BeloteState` from scratch — uniform sampling
wasn't enough, it needed to respect suit-following/over-trump history to
produce *consistent* worlds.

<Callout variant="lesson" title="Plain MCTSBot silently cheats on imperfect-information games">
  OpenSpiel's `MCTSBot` doesn't reject imperfect-information games outright —
  it runs against Belote without error. But `BeloteState` stores all four
  hands as plain visible attributes, so MCTS's tree search has full access to
  opponents' hidden cards during rollout. An omniscient bot in an evaluation
  pool produces misleading win-rate and Elo numbers for *every other* agent it
  plays against, not just itself. `ISMCTSBot`, which samples consistent worlds
  via `resample_from_infostate` instead of looking at the true state, is the
  only MCTS-family bot allowed in the project as a result.
</Callout>

<Callout variant="lesson" title="A second hidden RNG was silently breaking reproducibility">
  While hardening ISMCTS, a second, independent source of randomness was found
  quietly making runs non-reproducible even with a fixed seed — on top of an
  earlier randomness bug in `ISMCTSBot` itself that was fixed by implementing a
  seeded resampler. Seeding one obvious entry point isn't enough to guarantee
  reproducibility in a system with multiple stochastic components; every
  source needs to be found and pinned independently.
</Callout>

### Guided rollout & learned value function |#guided-rollout-value-function|

<PhaseJournal projectSlug="belote-ai" phaseId="guided-rollout-value-function" />

Exploring whether a heuristic or learned rollout policy beats ISMCTS's
default random rollouts. Both are currently inconclusive (see
[Future improvements](#future-improvements) below).

<Callout variant="lesson" title="A promising small-sample result didn't survive more data">
  An epsilon-greedy guided rollout looked like a real improvement over ISMCTS's
  default rollout at N=1,000 simulated deals (+1.13 pts/deal), but regressed to
  a statistically-indistinguishable -0.27 at N=10,000, with confidence
  intervals overlapping zero. Random, deterministic, and epsilon=0.3 rollouts
  all turned out to be indistinguishable at the tested simulation budget — a
  concrete example of why the harness reports confidence intervals rather than
  point estimates, and why a result needs to survive a larger sample before
  it's trusted.
</Callout>

## Architecture

The game engine (`BeloteGame`/`BeloteState`) lives in a personal OpenSpiel
fork rather than in `belote-ai` itself — a deliberate decision to build on
OpenSpiel's existing imperfect-information machinery and agent library
(uniform random, MCTS, ISMCTS, the CFR family) instead of re-implementing all
of that from scratch. `belote-ai` depends on the fork as an editable/path
install and owns only:

```
belote/
├── agents/
│   ├── registry.py         # name -> pyspiel.Bot factory
│   └── rule_valid_bot.py
├── eval/
│   ├── match.py            # evaluate_bots wrapper: duplicate deals, CIs, Elo
│   ├── decision.py         # decision-quality scoring
│   └── throughput.py       # games/sec benchmark
├── cli.py
└── tests/
```

Agents implement OpenSpiel's `Bot` contract directly (`step`, `restart_at`,
optional `inform_action`) rather than a bespoke interface, so legality is
enforced by `state.legal_actions()` and information hiding is enforced by
OpenSpiel itself — an agent only ever sees its own information state, never
the full game state, so it's structurally impossible for a correctly-written
bot to cheat.

## General decisions

Standing, project-wide choices that aren't tied to a single phase.

<Callout variant="decision" title="Build on OpenSpiel instead of a bespoke game engine">
  Belote is implemented as an OpenSpiel game rather than a standalone engine,
  inheriting its imperfect-information state model, a large library of
  ready-made agents (random, MCTS, ISMCTS, CFR), `evaluate_bots` for
  agent-vs-agent play, and built-in correctness tooling (`random_sim_test`,
  golden playthroughs). The trade-off: the game lives in a personal fork of
  OpenSpiel (`python_belote` isn't upstream yet), so belote-ai's
  reproducibility is currently tied to a pinned commit of that fork rather than
  a released package, until the game is upstreamed.
</Callout>

<Callout variant="decision" title="OpenSkill over TrueSkill for multi-agent ratings">
  OpenSkill was chosen for round-robin pool ratings over Microsoft's TrueSkill
  because it's MIT-licensed and patent-free, and it models team games (Belote's
  2v2 structure) natively rather than requiring a workaround.
</Callout>

<Callout variant="decision" title="Cap redeals instead of matching the official unlimited-redeal rule">
  If both bidding rounds end with everyone passing, official rules redeal
  indefinitely. The harness caps this at 10 attempts and treats an
  all-attempts-exhausted deal as a flat draw (all four `returns()` are 0)
  rather than an error — a deliberate, documented deviation from the official
  rules, made because every evaluation module needs a well-defined outcome for
  every deal, and an unbounded loop doesn't provide one.
</Callout>

## Approach

Every phase above was built and evaluated against the harness before moving
to the next, rather than assumed. That discipline paid for itself
repeatedly: it caught a plain-MCTSBot "cheat" (full hand visibility during
rollout), a hidden RNG silently breaking reproducibility, and a promising
epsilon-greedy result that looked real at 1,000 simulated deals but
collapsed to statistically indistinguishable at 10,000 — each one caught
before it could be mistaken for real progress.

## Future improvements

The immediate open problem is the learned value network (Guided rollout &
learned value function phase above), which is still losing decisively to
RandomISMCTS and shows two tangled issues: likely distribution shift between
the self-play data it was trained on and the positions it's evaluated on, and
clear overfitting (test loss plateaus around epoch 35 while training
continues to 200 with no early stopping). Isolating those two independently
is the next step, before deciding whether the value function is a viable
replacement for ISMCTS's rollouts at all. Longer term, the goal is to
upstream `python_belote` into `google-deepmind/open_spiel` so the project no
longer depends on a personal fork for its core game implementation.
