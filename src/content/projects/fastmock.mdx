## Overview

A PyPI-published FastAPI middleware that mocks route responses directly
from what's already declared: `responses={status_code: {"model":
SomeModel}}`. Add the middleware, optionally decorate a route with
`@mock(...)`, and an endpoint returns a `polyfactory`-generated instance of
its own declared response model instead of a hand-written stub — so the
mocked shape can't drift from the real one, since there's only one model to
begin with. Layered overrides (decorator, middleware default, request
header) let element counts, status codes, latency, and failure rates be
dialed in per route or per request, and request validation (opt-out)
returns the same `422` a real implementation eventually would.

The initial commit is from June 2024. The project sat untouched for two
years until it was picked back up in one sitting on 2026-08-08, which
modernized the whole toolchain and shipped the two features, fault
injection and request validation, that took it from a toy to something
worth publishing.

## Problem

- **Hand-written stubs drift from the real model.** A stub response for a
  not-yet-implemented endpoint is repetitive to write and easy to leave
  out of sync the moment the response model changes.
- **Existing alternatives don't give per-route control.** Other FastAPI
  mocking libraries exist (`fastapi-mock`, `fastapi-mock-middleware`), but
  none combine per-route status overrides, header-driven runtime overrides,
  fault injection, and real request validation in one package.
- **Testing failure handling needs a fake failure path.** Verifying how a
  client handles a slow or unreliable upstream normally means either
  hand-rolling a fake failure branch or standing up a real flaky server.
- **A mock still needs to reject a malformed request, without a real
  implementation to reject it.** An endpoint with no real body should
  still return FastAPI's own `422` on a bad request, but without needing
  the eventual real implementation's `Depends(...)` (auth, DB session) to
  exist or run just to validate.
- **The 2024 code itself had rotted.** `setup.py`/`requirements*.txt`
  packaging, deprecated Pydantic v1 calls left in place despite a
  `pydantic>=2` dependency pin, and an OpenAPI test asserting the full
  `/openapi.json` body verbatim, breaking on any FastAPI/Pydantic patch
  release that reformatted schema output.

### Core mocking |#core-mocking|

`FastMockDecorator` stores a `MockData` instance as an attribute on the
decorated route function. `FastMockMiddleware.dispatch` matches the
incoming request to a FastAPI `APIRoute` by regex-ing its path template
(`get_matched_route`, since middleware runs before Starlette's own router
has resolved anything), merges `MockData` from four sources in precedence
order, and hands the result to `get_response`. That function looks up the
declared model for whichever status code applies and generates it via
`polyfactory`: a `Sequence`/`Mapping` response model recurses per-element
through `get_model_factory`, everything else calls straight into a
`polyfactory` factory or its Faker provider map.

<Callout variant="decision" title="type=example reads a model's own OpenAPI example, it isn't a separate example store">
  Setting `type=GenerationTypeEnum.example` doesn't feed FastMock a
  separate example value — it reaches into the response model's own
  `model_config["json_schema_extra"]["example"]`, the same field FastAPI
  already renders into its docs. No example on the model means an
  explicit exception rather than a silently empty response, since a
  documented example is exactly what `type=example` promises.
</Callout>

### Modernize tooling |#modernize-tooling|

Two years after the initial commit, the whole toolchain got rebuilt in one
pass: `setup.py` + `requirements*.txt` gave way to a hatchling-based
`pyproject.toml` and `uv.lock` with `test`/`lint`/`docs`/`dev` dependency
groups, `fastmock/py.typed` was added for PEP 561 compliance, and CI now
installs `uv` and runs the test matrix across Python 3.10-3.13 instead of
`pip install -r requirements.txt`.

<Callout variant="lesson" title="A pydantic>=2 pin doesn't mean the code is on the v2 API">
  `.dict()` and `.copy(update=...)` still work as deprecated aliases under
  Pydantic 2.x, so nothing failed loudly even though the dependency had
  been pinned to `pydantic>=2` the whole time. The v1-style calls in
  `decorator.py`, `middleware.py`, and `tools.py` only got caught by
  actually reading the code, not by CI going red, and were replaced with
  `.model_dump()`/`.model_copy(update=...)`.
</Callout>

### Fault injection |#fault-injection|

`delay` and `fail_rate`/`fail_status_code` on `MockData` simulate a slow
or unreliable upstream without writing any extra code. `get_response`
became async to support `delay` via `asyncio.sleep`; `fail_status_code`
must be one of the route's declared `responses`, the same rule that
already applied to `response_status_code`.

Both fields were already reachable via decorator, middleware default, and
the `X-FASTMOCK-*` header the moment they were added to `MockData`, since
that retrieval path is generic over whatever fields the model has — no
extra wiring needed per feature.

### Request validation |#request-validation|

`validate_request` (default `True`) checks a request's path, query,
header, cookie, and body parameters against the endpoint's declared types
before generating a mock response, returning FastAPI's own `422` shape on
a mismatch. `get_request_validation_errors` reuses FastAPI's own
`request_params_to_args`/`request_body_to_args`
(`fastapi.dependencies.utils`) rather than reimplementing type coercion,
so it stays correct as FastAPI's own validation logic evolves.

<Callout variant="decision" title="Depends(...) is never resolved while mocking a route">
  `get_request_validation_errors` only validates `dependant.path_params`,
  `query_params`, `header_params`, `cookie_params`, and `body_params` — it
  deliberately never calls `solve_dependencies` or walks
  `dependant.dependencies`. A mocked route has no real implementation to
  protect; running a route's real `Depends(...)` (auth, a DB session) just
  to validate a request nobody is actually going to serve for real would
  defeat the point of mocking it.
</Callout>

<DecisionTable
  decisions={[
    {
      label: 'Type coercion',

The new test file covers a valid request passing through without ever
calling the route's `Depends()` dependency, an invalid body / missing
query param / malformed JSON body all returning FastAPI-shaped 422s while
still never calling the dependency, and `validate_request=False` disabling
the check entirely.

## Approach

Every feature reuses FastAPI's or Pydantic's own machinery instead of
reimplementing it: `polyfactory` generates data straight from a model's
own field types rather than a bespoke generator, request validation reuses
FastAPI's own argument-resolution functions for byte-identical `422`
shapes, and every new `MockData` field (`delay`, `fail_rate`,
`validate_request`) becomes overridable through the decorator, the
middleware default, and the request header simultaneously, for free,
because all three layers are generic over whatever fields `MockData`
happens to have rather than wired per-feature.

## Future improvements

Grounded in the project's own README comparison table and what the code
currently does:

- **Multiple examples, randomly chosen per request**, closing the one gap
  FastMock's own comparison table concedes to `fastapi-mock` today: a
  route's `type=example` reads a single fixed `model_config` example
  rather than picking from several.
- **Non-JSON response mocking.** `get_response` always returns a
  `JSONResponse`; a route documented with a non-JSON response type has no
  way to be mocked to that shape.
