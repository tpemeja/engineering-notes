## Overview

A PyPI-published FastAPI middleware that mocks route responses directly
from what's already declared: `responses={status_code: {"model":
SomeModel}}`. Add the middleware, optionally decorate a route with
`@mock(...)`, and an endpoint returns a `polyfactory`-generated instance of
its own declared response model instead of a hand-written stub — so the
mocked shape can't drift from the real one, since there's only one model to
begin with. As of 0.2.0 that response is also a pure function of the
request: the same call returns the same plausible, field-name-aware data
every time, across refreshes, restarts, and machines, while fault
injection stays genuinely random on top of it.

The initial commit is from June 2024. The project sat untouched for two
years until it was picked back up on 2026-08-08–09, which modernized the
whole toolchain, shipped fault injection and request validation, and then
— in the 0.2.0 push the very next day — made output deterministic and
plausible, added a factory escape hatch for invariants no schema can
express, and wrote a roadmap page that says out loud what fastmock will
never try to do.

## Problem

- **Hand-written stubs drift from the real model.** A stub response for a
  not-yet-implemented endpoint is repetitive to write and easy to leave
  out of sync the moment the response model changes.
- **Existing alternatives don't give per-route control.** Other FastAPI
  mocking libraries exist (`fastapi-mock`, `fastapi-mock-middleware`), but
  none combine per-route status overrides, header-driven runtime overrides,
  fault injection, and real request validation in one package.
- **Testing failure handling needs a fake failure path.** Verifying how a
  client handles a slow or unreliable upstream normally means either
  hand-rolling a fake failure branch or standing up a real flaky server.
- **A mock still needs to reject a malformed request, without a real
  implementation to reject it.** An endpoint with no real body should
  still return FastAPI's own `422` on a bad request, but without needing
  the eventual real implementation's `Depends(...)` (auth, DB session) to
  exist or run just to validate.
- **Random output makes a mock unusable for demos and integration tests.**
  Two identical requests returning different data means a demo jumps
  around on refresh, a screenshot can't be relied on, and a test can't
  assert against a literal payload.
- **A field's type alone doesn't say what it means.** A `country: str`
  field generated an arbitrary 20-character string, correct by type but
  useless at a glance, and some invariants (an order total matching its
  line items) aren't expressible as a type at all.
- **The 2024 code itself had rotted.** `setup.py`/`requirements*.txt`
  packaging, deprecated Pydantic v1 calls left in place despite a
  `pydantic>=2` dependency pin, and an OpenAPI test asserting the full
  `/openapi.json` body verbatim, breaking on any FastAPI/Pydantic patch
  release that reformatted schema output.

### Core mocking |#core-mocking|

`FastMockDecorator` stores a `MockData` instance as an attribute on the
decorated route function. `FastMockMiddleware.dispatch` matches the
incoming request to a FastAPI `APIRoute` (`get_matched_route`, since
middleware runs before Starlette's own router has resolved anything),
merges `MockData` from four sources in precedence order, and hands the
result to `get_response`. That function looks up the declared model for
whichever status code applies and generates it via `polyfactory`: a
`Sequence`/`Mapping` response model recurses per-element through
`get_model_factory`, everything else calls straight into a `polyfactory`
factory or its Faker provider map.

<Callout variant="decision" title="type=example reads a model's own OpenAPI example, it isn't a separate example store">
  Setting `type=GenerationTypeEnum.example` doesn't feed FastMock a

  `model_config["json_schema_extra"]["example"]`, the same field FastAPI
  already renders into its docs. No example on the model means an
  explicit exception rather than a silently empty response, since a
  documented example is exactly what `type=example` promises.
</Callout>

### Modernize tooling |#modernize-tooling|

Two years after the initial commit, the whole toolchain got rebuilt in one
pass: `setup.py` + `requirements*.txt` gave way to a hatchling-based
`pyproject.toml` and `uv.lock` with `test`/`lint`/`docs`/`dev` dependency
groups, `fastmock/py.typed` was added for PEP 561 compliance, and CI now
installs `uv` and runs the test matrix across Python 3.10-3.13 instead of
`pip install -r requirements.txt`.

<Callout variant="lesson" title="A pydantic>=2 pin doesn't mean the code is on the v2 API">
  `.dict()` and `.copy(update=...)` still work as deprecated aliases under
  Pydantic 2.x, so nothing failed loudly even though the dependency had
  been pinned to `pydantic>=2` the whole time. The v1-style calls in
  `decorator.py`, `middleware.py`, and `tools.py` only got caught by
  actually reading the code, not by CI going red, and were replaced with
  `.model_dump()`/`.model_copy(update=...)`.
</Callout>

### Fault injection |#fault-injection|

`delay` and `fail_rate`/`fail_status_code` on `MockData` simulate a slow
or unreliable upstream without writing any extra code. `get_response`
became async to support `delay` via `asyncio.sleep`; `fail_status_code`
must be one of the route's declared `responses`, the same rule that
already applied to `response_status_code`.

### Request validation |#request-validation|

`validate_request` (default `True`) checks a request's path, query,
header, cookie, and body parameters against the endpoint's declared types
before generating a mock response, returning FastAPI's own `422` shape on
a mismatch. `get_request_validation_errors` reuses FastAPI's own
`request_params_to_args`/`request_body_to_args`
(`fastapi.dependencies.utils`) rather than reimplementing type coercion,
so it stays correct as FastAPI's own validation logic evolves.

<Callout variant="decision" title="Depends(...) is never resolved while mocking a route">
  `get_request_validation_errors` only validates `dependant.path_params`,
  `query_params`, `header_params`, `cookie_params`, and `body_params` — it
  deliberately never calls `solve_dependencies` or walks
  `dependant.dependencies`. A mocked route has no real implementation to
  protect; running a route's real `Depends(...)` (auth, a DB session) just
  to validate a request nobody is actually going to serve for real would
  defeat the point of mocking it.
</Callout>

<DecisionTable
  decisions={[
    {
      label: 'Type coercion',
      chose: "Reuse FastAPI's own request_params_to_args / request_body_to_args",
      insteadOf: 'Hand-rolled parameter and body type checking',
      why: "Stays correct as FastAPI's own validation logic evolves, and produces byte-identical 422 error shapes without a second implementation to keep in sync.",
    },
    {
      label: 'Validation order',
      chose: 'After delay, before the fail_rate roll',
      insteadOf: 'Before delay, or after the fail_rate roll',
      why: 'A malformed request always gets a deterministic 422, not a simulated random failure, while delay still applies either way to simulate real latency regardless of outcome.',
    },
  ]}
/>

<Callout variant="lesson" title="Every route with a path parameter always 422'd, and no test caught it">
  Middleware runs before Starlette's router populates `request.path_params`,
  so `validate_request` saw every path parameter as missing — `GET
  /items/42` against a route declared as `/items/{item_id}` failed
  validation with the default settings on. `get_path_params` now resolves
  them explicitly by calling `api_route.matches(request.scope)` itself. No
  existing test declared a path parameter, which is how it shipped
  unnoticed.
</Callout>

The test file for this feature covers a valid request passing through
without ever calling the route's `Depends()` dependency, an invalid body /
missing query param / malformed JSON body all returning FastAPI-shaped
422s while still never calling the dependency, and
`validate_request=False` disabling the check entirely.

### Deterministic responses |#deterministic-responses|

0.2.0's headline change. Before it, two identical requests returned
different data, which made demos jump around on refresh and made
integration tests impossible to write against a literal payload. The
contract is now that **a response is a pure function of the request**:
`fastmock/seeding.py` derives a seed from the configured base
`MockData.seed`, the request method, path, sorted query string, and a
canonicalised body (JSON re-serialised with sorted keys; form/multipart
bodies excluded; only the first 64KB hashed), then reseeds polyfactory
immediately before generation with no `await` in between, since the
seeded state is shared process-wide.

  source={{
    name: 'Incoming request',
    detail: 'method + path + sorted query string + canonicalised body',

  branchLabel="two independent sources of variation"
  branches={[
    {
      name: 'Response payload — seeded',
      detail: 'blake2b hash of the request, mixed with MockData.seed, reseeds polyfactory + Faker right before generation: deterministic',
    },
    {
      name: 'Fault injection — unseeded',
      detail: "fail_rate calls random.random() directly; polyfactory's seed_random never touches the stdlib random module, so failures stay genuinely random",
    },
  ]}
  mergeLabel="both feed the same request/response cycle"
  merge={{
    name: 'JSONResponse',
    detail: 'deterministic payload, non-deterministic outcome',
  }}
/>

<Callout variant="lesson" title="A seed alone doesn't make temporal values reproducible">
  Every one of polyfactory's temporal providers is anchored to the current
  clock: `datetime` spans "-30y" to "now", `date` is bounded by today,
  `time` and `timedelta` are measured from now. A seed fixes the *offset*
  from that clock, not the value itself, so a `created_at` field still
  drifted a little between two runs seconds apart — silently violating the
  "pure function of the request" guarantee. `StableTemporalFactoryMixin`
  draws all four types from a fixed 2000–2035 window instead, confirmed by
  regression tests that were checked to fail without the fix.
</Callout>

<DecisionTable
  decisions={[
    {
      label: 'Default behaviour',
      chose: 'seed=1 by default, deterministic out of the box',
      insteadOf: 'Opt-in determinism (seed=None by default)',
      why: 'A documented breaking change in 0.2.0: most callers want stable demos and tests more than they want request-to-request variety, and variety is still one field away (seed=None).',
    },
    {
      label: 'Body canonicalisation',
      chose: 'Re-serialise JSON with sorted keys before hashing',
      insteadOf: 'Hash the raw request bytes',
      why: "Two clients sending the same logical payload with different key ordering or incidental whitespace should get the same response, not two different stable ones.",
    },
  ]}
/>

### Plausible generation |#plausible-generation|

Factory selection moved out of `get_mock_factory_class` scanning
`BaseFactory.__subclasses__()` — which reports only *direct* subclasses,
is populated by import side effects, and made selection order-dependent —
into `fastmock/factories.py`'s explicit, ordered `DEFAULT_BASE_FACTORIES`
tuple (`ModelFactory`, `DataclassFactory`, `TypedDictFactory`). A new
`DEFAULT_PROVIDER_MAP` then teaches those factories to look at a field's
*name*, not just its type: a field called `country` now returns a country
instead of a random string, via a `NameAwareFactoryMixin` layered over
each base factory.

<DecisionTable
  decisions={[
    {
      label: 'Factory selection',
      chose: 'An explicit ordered registry in fastmock/factories.py',
      insteadOf: 'Scanning BaseFactory.__subclasses__() at call time',
      why: '__subclasses__() only reports direct subclasses and is populated by import side effects, so selection order depended on what happened to already be imported, and any factory subclassing ModelFactory rather than BaseFactory directly was never found.',
    },
    {
      label: 'Name-based inference',
      chose: 'A small, exact-match field-name → Faker provider map, gated on an exact type match',
      insteadOf: 'Guessing from a substring or suffix, or trusting a name match unconditionally',
      why: "A plausible-looking but wrong value is worse than obvious gibberish — gibberish tells you to reach for a custom factory, a wrong value silently misleads. The exact-type gate keeps a city field typed int an int, and stops a datetime provider from being accepted for a date field.",
    },
    {
      label: 'provider_map placement',
      chose: 'A FastMockMiddleware constructor argument',
      insteadOf: 'A MockData field',
      why: "It's global policy rather than a per-request value, and being a mapping of callables it couldn't ride the X-FASTMOCK-* header channel anyway — the rule later reused for factory.",
    },
  ]}
/>

<Callout variant="lesson" title="isinstance(x, type) on a parameterised generic differs between Python 3.10 and 3.11+">
  `isinstance(list[str], type)` is `True` on 3.10 but `False` from 3.11
  onward, which made `resolve_annotation` return the bare generic itself
  on 3.10 instead of `None`. Behaviour was unaffected in practice — a
  generic never satisfies `is_compatible`'s exact-type-match requirement
  either way — but the version-dependent branch was worth removing at the
  source rather than leaving it to coincidence. Verified against 3.10
  through 3.13.
</Callout>

Deliberately absent from the default map: a bare `name`, too ambiguous to
guess (a product, a bank, and a person are all equally plausible), left to
`polyfactory` itself. Semantic types like `EmailStr` are left alone too —
they already resolve correctly by type, so a name-based override would be
redundant at best.

### Custom factory escape hatch |#custom-factory-escape-hatch|

Schema-driven generation produces fields that are individually plausible
but unrelated: an order `total` that doesn't match its `line_items`, a
`shipped` order with no `tracking_number`. Those invariants live in the
caller's domain, not the schema, so fastmock doesn't guess at them.
`MockData.factory` accepts a caller-supplied `polyfactory` factory that
builds the response instead of one derived automatically from the model —
applied per element for list responses, and taking precedence over `type`
as the more specific instruction.

<DecisionTable
  decisions={[
    {
      label: 'Precedence',
      chose: 'factory overrides type whenever both are set',
      insteadOf: 'Treating the two as independent or mutually exclusive',
      why: 'A caller who supplies a factory has already opted out of schema-driven generation for that route; type would otherwise be ambiguous about which generation path wins.',
    },
    {
      label: 'Configuration channel',
      chose: 'A MockData field that cannot travel over an X-FASTMOCK-* header',
      insteadOf: 'Trying to make it header-settable like every other MockData field',
      why: "It's a callable — there's no sane string encoding for a polyfactory factory in a header value, the same non-scalar rule provider_map already followed on the middleware constructor.",
    },
  ]}
/>

<Callout variant="lesson" title="An unmockable model raised the wrong exception">
  The fallback error path read `model.response_model.__name__`, but by
  that point `model` already *is* the response model — it has no
  `response_model` attribute of its own. Hitting an unsupported type
  raised a confusing `AttributeError` instead of the intended
  `ValueError: Cannot mock ...`. Found and fixed alongside the factory
  escape hatch, not by a dedicated bug hunt.
</Callout>

### Worked example & roadmap |#worked-example|

Two additions that turn the feature list into something a new user can
actually evaluate. `documentation/docs/roadmap.md` states fastmock's
positioning explicitly — a **realistic fake backend** for QA, staging,
demos, and integration tests, pointed at `fastapi-mock`'s
`raise NotImplementedError()` for the lower-friction "haven't built this
yet" case — and three permanent scope boundaries. `examples/storefront.py`
plus its walkthrough page exercise every feature together against one
realistic API: name- and type-inferred customer data, seed-stable
pagination, an `OrderFactory` encoding the total/tracking-number
invariants, a custom `sku` provider, validation without declaring a 422,
and the full header-override table.

  decisions={[

## Approach

Every feature reuses FastAPI's, Pydantic's, or polyfactory's own machinery
instead of reimplementing it: request validation reuses FastAPI's own
argument-resolution functions for byte-identical `422` shapes, seeding
reuses polyfactory's own `seed_random` rather than a bespoke RNG, and
route/path-parameter matching now delegates to Starlette's real
`APIRoute.matches` instead of an approximation. Configuration follows one
consistent rule as the surface has grown: `MockData` holds per-route and
per-request knobs (`element_size`, `delay`, `seed`, `factory`), and the
`FastMockMiddleware` constructor holds global policy
(`retrieve_data_function_list`, `provider_map`). Every scalar on
`MockData` is therefore overridable per-request through an `X-FASTMOCK-*`
header for free; the two things that can't travel that way, `factory` and
`provider_map`, are exactly the two non-scalar options, which is why both
ended up on a different layer rather than by accident.

## Future improvements

FastMock is stable and not under active development right now, so this is a
list of known gaps rather than a roadmap. fastmock's own `roadmap.md`
separates permanent non-goals (hand-written payloads, cross-field coherence
without an explicit factory, statefulness — see Worked example & roadmap
above) from genuine gaps. Two of the latter remain, grounded in the
README's own comparison table and what the code currently does, if work on
this picks back up:

- **Multiple examples, randomly chosen per request** — still the one row
  FastMock's own comparison table concedes to `fastapi-mock`: `type=example`
  reads a single fixed `model_config` example rather than picking from
  several.
- **Non-JSON response mocking.** `get_response` always returns a
  `JSONResponse`; a route documented with a non-JSON response type has no
  way to be mocked to that shape.
