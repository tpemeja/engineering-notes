## Overview

FastSpec is a web app for writing and maintaining OpenAPI specs. You build a
spec in a form or as YAML or JSON, preview it in Swagger UI, save it as named
versions, diff any two of them, and lint it with Spectral against your own
house rules. An MCP server lets AI agents such as Claude Code or Cursor read,
write, version and lint your specs with a scoped API key.

It is the spec-first counterpart to [FastMock](/projects/fastmock), which mocks
an API from the models a FastAPI app already declares. FastSpec has been open
source (AGPL-3.0) since v0.1.0 on 27 September 2026. It runs from one Docker
image, or as a hosted version at
[fastspec.kaseovo.com](https://fastspec.kaseovo.com). Every screenshot below
comes from the app running locally against fictional specs.

Work is paused since v0.3.0 on 2 October 2026. The hosted version keeps
running, and Dependabot still opens a pull request per ecosystem each month.

## Problem

- **OpenAPI is easy to get subtly wrong by hand.** Path parameters, `$ref`s and
  array item schemas all have to line up, and Swagger UI often fails quietly
  when they don't.
- **Reviewers need changes in API terms.** "An endpoint was removed" and "a
  schema field became required" matter; a JSON text diff buries them.
- **Custom lint rules are a code execution risk.** Spectral rulesets can load
  JavaScript from disk and fetch other rulesets from URLs, so accepting them
  from users as-is means running their code on the server.
- **AI clients need their own credential.** Handing an assistant the user's
  web session is not acceptable; access has to be scoped and revocable.
- **Trying it has to take one command.** Until September 2026, running it
  locally meant an AWS emulator, the AWS CDK and a Google OAuth client of your
  own.
- **It is a side project.** The AWS bill has to be close to zero when nobody
  is using it, without giving up a real managed Postgres.

## Approach

I built FastSpec with AI coding agents in the loop (Claude Code, and GitHub's
Copilot agent for some issues), so the repo is written to be read by an agent
as much as by me. `AGENTS.md` lists the test commands and what the common
failures mean, `CONTEXT.md` is a glossary of domain terms (Path Parameter
Token, Lint Ruleset, Spec Version Mode), and every architecture decision is an
ADR. Once the feature set was in place I ran a full-repo review and worked
through it.

The rule the codebase follows throughout: **the why lives next to the code.**
Module docstrings point at the ADR or review section that explains them.
`database.py`, for example, cites ADR-0009 for why the hosted database's quota
errors get their own message instead of "try again shortly". A deliberate
trade-off then can't get "fixed" by accident, by me or by an agent.

Going open source followed the same habit. `docs/ROADMAP.md` records each
decision with its reason (license, sign-in, database, what to do with the git
history), ticks off the work as it lands, and says what keeps running while
the project is paused. Every release has a changelog entry.

<Phase

  title="Form editor"
  status="done"
  goal="Let someone write a complete OpenAPI spec without knowing its JSON shape by heart, with the code and a live Swagger preview one click away."
  outcome="A full spec can be built without touching JSON, and path parameters can't drift from the path string."

The editor is three views over one spec object: a form, the code in Monaco
(YAML or JSON), and a Swagger UI preview. Most of the work went into the form.
Info, servers, paths, tags, component schemas and security each get a section
with search, and adding a path, an operation or a schema goes through a short
wizard instead of an empty JSON block.

Path parameters are the one thing the form won't let you edit directly. Type
`/loans/{loanId}/return` and a required `loanId` path parameter appears;
remove the token and the parameter goes too, after a confirmation if you had
filled it in. The path string is the only source, so the two can't disagree.

Every spec keeps named versions. The backend diff compares two of them in API

what changed and the lint score the new version would get. The report also
exports as Markdown, for a PR description or a changelog.

<Phase
  id="custom-lint-rules"
  title="Linting with custom rules"
  status="done"
  goal="Catch spec problems before an API consumer does, with house rules a team can write without learning Spectral's YAML and without being able to run code on the server."
  outcome="Specs lint against Spectral's OpenAPI rules plus named custom rulesets, with no path to run user code."
>

Linting runs the Spectral CLI, installed in the backend's Docker image, against
a stored spec or an unsaved draft. Spectral's `spectral:oas` rules always
apply. On top of them, a user keeps any number of named rulesets, marks one as
the default, and can pin another to a specific spec: a strict one for a public
API, a looser one for an internal one. In the code view, each finding's marker
is placed by its JSON path, so it lands on the right line in YAML and in JSON.

Rules are built in a form (severity, a JSONPath target from presets, a
function and its options), with a raw YAML tab for what the form can't
express. "Test against current spec" runs one draft rule on its own, without
the baseline rules, so you see exactly what it matches before saving.

<Callout variant="warning" title="In FastAPI, route order is part of the contract">
  The lint router mixes static paths (`/rulesets`, `/preview-rule`) with
  catch-alls (`/{spec_id}`). FastAPI matches routes in registration order, so
  if the catch-all came first, `POST /lint/rulesets` would try to lint a spec
  whose id is "rulesets". Static routes are registered first, with a comment
  in the router saying why.
</Callout>

<Phase
  id="mcp-server"
  title="MCP server for AI clients"
  status="done"
  goal="Let an AI assistant work with a user's specs directly, with a credential the user can scope and revoke, and without ever touching their web session."
  outcome="An API key scoped by action reads, writes, versions, compares and lints its owner's specs through eleven MCP tools."
>

A FastMCP server runs in the same app at `/mcp`. It started with three read
tools (`who_am_i`, `get_saved_specs_for_user` and `get_spec_details`). v0.1.0
added tools to create and delete specs, list, read and save versions, compare
two of them, validate and lint, all reusing the services behind the HTTP API.

AI clients never see the web session. Instead, a user creates an API key in
the app, picks what it may do (`read:specs`, `write:versions`, `lint:specs`
and so on), and adds it with the MCP URL to their client. Each tool declares
the actions it needs, and a middleware checks them before the call runs.

<Callout variant="warning" title="FastAPI doesn't run a mounted app's lifespan">
  FastMCP's streamable-HTTP session manager starts in its app's lifespan, and
  FastAPI skips the lifespans of mounted sub-apps, so until v0.1.0 every MCP
  call failed with "task group is not initialized". Sharing one manager isn't
  the fix either: it can only start once, and on Lambda, Mangum runs a fresh
  lifespan per invocation. The endpoint now runs stateless and builds a
  short-lived handler for each request.
</Callout>

</Phase>

only needed to work on the AWS deployment itself.

<Callout variant="lesson" title="The wake machinery never worked">
  In September 2026 it turned out to fail twice over. The wake page checked
  the liveness endpoint, which answers while
  the database sleeps, so it reported "already up". And backend cold starts
  refreshed the timestamp the wake Lambda's cooldown read, so a visit to the
  site disabled waking. Its tests still covered the ECS services of the
  Fargate era, and nothing ran them. A day after the fix, all of it was
  deleted (see the last phase).
</Callout>

<Callout variant="warning" title="CloudFormation won't put an SSM SecureString in a Lambda environment variable">
  `{{resolve:ssm-secure:...}}` dynamic references only work on a short list of
  resource properties, and Lambda environment variables are not on it. The
  Lambda gets the parameter *names* instead and fetches the values from SSM at
  cold start, so no secret appears in the console or the template.
</Callout>

</Phase>

<Phase
  id="open-source"
  title="Self-hosting and open source"
  status="done"
  goal="Make FastSpec something a stranger can try with one command and read the code of, without a Google Cloud project, an AWS account or a Postgres server."

The root `Dockerfile` builds the SPA, installs a pinned Spectral CLI and serves
everything on port 8080. In production, CloudFront sends `/specs` to S3 and
`/api`, `/auth` and `/mcp` to the Lambda; `frontdoor.py` does the same routing
inside the app, so sign-in behaves the same in both. With no configuration,
the container runs in single-user mode on SQLite, applies its migrations and
generates its JWT secret into `/data`. Each release publishes it for amd64
and arm64.

The same release made the editor worth trying on a real spec: YAML editing
(specs are still stored as JSON), import by dropping, choosing or pasting a
file, download as YAML or JSON, a Petstore example on the first visit, and
Swagger UI bundled instead of loaded from a CDN. Before publishing, ruff and
ESLint went from about 300 and 1,500 findings to none, enforced in CI, and
the backend's dependencies were pinned.

<Callout variant="warning" title="Never link OIDC accounts by email">
  Email is mutable at many providers, so matching on it lets someone take over
  an account by changing theirs (the "nOAuth" class of bugs). Accounts are
  keyed on the issuer and `sub`, and a sign-in whose email matches an account
  with a different `sub` is refused, not linked. The server also refuses to
  start on contradictory auth settings, so a forgotten `AUTH_MODE=oidc` can't
  leave a public instance open.
</Callout>

<Callout variant="lesson" title="Packaging it for strangers was the best test">
  Making it run with no setup found bugs months of use hadn't. The MCP server
  had never worked, CI never ran the backend tests (pytest wasn't installed),
  logging out didn't revoke the session on the server, version comparisons
  showed added endpoints as removed, and unpinned SQLAlchemy 2.1 would have
  broken Postgres connections on the next image build.
</Callout>

<Phase
  id="near-zero-cost"
  title="Near-zero hosting cost"
  status="done"
  goal="Bring the hosted version's idle month from about $17 down to cents, without a multi-minute wake-up."
  outcome="Neon's free plan instead of RDS: an idle month costs about $0.03, and the first request after 5 idle minutes waits under a second."
>

A stopped RDS instance still cost about $17 a month. RDS bills the
provisioned disk (100 GB, the CDK default) and backups while stopped, and AWS
restarts a stopped instance after seven days anyway. Waking it took one to
three minutes.

The backend now takes any Postgres as a connection string from SSM. The
hosted version uses Neon's free plan in AWS Singapore: it scales to zero
after 5 idle minutes and resumes on the next connection in under a second, so
there is nothing left to wake. The data and wake stacks, the wake page and
the "waking up" screen were deleted, and moving the domain's DNS to
Cloudflare, where the parent domain already lived, removed FastSpec's Route
53 zone.

v0.3.0 then added an email on every first sign-in, through an SNS topic, and
cut the backend's log retention to 30 days, since sign-in logs can hold email
addresses.

<Callout variant="warning" title="Lambda Function URLs strip the trailing slash">
  `/api/specs/` reached FastAPI as `/specs`, which only matched `/specs/`
  through a redirect. FastAPI built it from the Host header, the function's
  own URL, so the browser followed it cross-origin and got two
  Access-Control-Allow-Origin headers, one from the Function URL and one from
  the app. The API now ignores trailing slashes and never redirects for them,
  and the Function URL has no CORS settings: only CloudFront calls it.
</Callout>

<Callout variant="warning" title="Neon's free-plan API only reports storage">
  The first usage check read compute time and data transfer from Neon's API.
  On the free plan both stay at zero, as fields of its old pricing, so it could
  never have warned about compute. It now checks storage, and whether the app
  can reach its database at all, which is how a used-up compute allowance
  shows.
</Callout>

<Callout variant="lesson" title="Smoke-test the image you ship">
  On the hosted version, lint failed with "Spectral CLI not found". Amazon
  Linux 2023 links global npm commands into `/usr/bin`, and the configured
  path pointed at `/usr/local/bin`. Nothing had ever linted through the Lambda
  image. Its build now runs the CLI from the configured path, and CI starts
  both images and lints through them.
</Callout>

## Future improvements

- **The diff ignores parameters.** It compares summaries and request and
  response schemas, so a new query parameter doesn't show up as a change.
- **Lint pays a Node cold start per call.** An HTTP sidecar transport exists
  in `spectral_client.py` with no server behind it yet, and results aren't
  cached by spec and ruleset hash.
- **YAML comments don't survive a save.** Specs are stored as JSON, so keeping
  them means storing the raw text and reworking versions and diff.
- **The hosted app connects as the database owner.** The least-privilege
  `fastspec_app` role exists as a migration, but it only runs when
  `FASTSPEC_APP_DB_PASSWORD` is set, and the Neon deployment doesn't set it.
- **The hosted database keeps 6 hours of history.** Neon's free plan has no
  long-term backup, so anything worth keeping has to be exported.
- **One OIDC provider at a time, and no GitHub sign-in.** GitHub doesn't
  support OIDC for user sign-in, so it would need its own OAuth2 provider.
