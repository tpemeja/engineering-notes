## Overview

The backend behind my wife's Instagram Creator account. It started as a way
to stop the [Instagram Insight](/projects/instagram-insight/) tablet from being the
only place the account's history lived, and grew into the one service
everything else talks to.

It receives Meta's webhooks for comments and messages, asks an LLM what each
comment needs and drafts a reply, polls post and account insights on a
schedule, and exposes all of it through one API. Once a day it also builds a
media kit, the figures a brand asks for, which Claude and ChatGPT can read
as an MCP tool. The tablet and the
[Insight Dashboard](/projects/instagram-dashboard/) website are both
clients of it. Everything scales to zero, so it costs close to nothing when
nothing is happening.

## Problem

- **The history lived on one tablet.** Instagram only ever exposes a post's
  current totals, so the daily snapshots the tablet kept were the only copy
  that would ever exist. A factory reset would lose them for good.
- **Meta's API fails silently.** The wrong parameter shape returns HTTP 200
  with an empty `data: []`, never an error. A schema built on a guess would
  store nothing and look healthy, and a 30-day reach added up from daily
  rows counts a returning viewer once per day.
- **Scale-to-zero fights a five-minute schedule.** Aurora Serverless only
  pauses after five minutes with no query, so a poller that touches Postgres
  every few minutes keeps it awake, and billed, all month.
- **Replies are published under someone else's name.** An LLM can suggest,
  but a wrong reply or a wrong delete on a real account cannot be undone.
- **Tokens are hard to replace and easy to over-grant.** Losing the
  Instagram token means a browser consent flow that needs the account owner
  in person, so exactly one thing may rotate it. An AI app given the media
  kit must see nothing else, and lose access without logging out the tablet.

## Approach

Analysis and acting are kept apart everywhere. The processor writes a
suggested action and a draft, and nothing in this repo acts on it by itself.
A write to Instagram only happens when a client calls the proxy after a
person confirms. The same split runs through the data: a decision is always
reproducible from what was stored (prompt version, policy version, raw
response), and "not measured" is `null`, never `0`, so a gap never reads
as a real zero. The MCP tool tells the model the same thing.

I verified every Graph API behavior against the live account before
designing a table around it, with a spike script whose raw responses are
checked in as test fixtures.

<Phase
  id="webhook-ingestion"
  title="Webhook ingestion"
  status="done"
  goal="Accept Meta's webhooks for comments, messages and mentions without ever losing one, while staying fast and cheap at the edge."
  outcome="Every webhook is signature-checked, stored twice and queued, or answered with a 500 so Meta retries."
>

The webhook Lambda sits behind a bare Function URL and does one job. It
never runs FastAPI, so ingestion carries none of the API's cold-start cost.
The order of writes is what makes it safe to retry:

1. Check the `X-Hub-Signature-256` HMAC, rejecting forgeries with `403`.
2. Write the raw payload to S3 (safe to repeat).
3. Claim the event in DynamoDB with `attribute_not_exists(event_id)`.
4. Send a small reference to SQS. If that fails, delete the claim and
   return `500`.

<Callout variant="lesson" title="An idempotency claim has to be rolled back if the next step fails">
  Without step 4's rollback, a failed SQS send leaves a claimed event behind.
  Meta's retry then looks like a duplicate, gets a `200`, and the event never
  reaches the queue. The handler only returns `200` once the event is both
  stored and queued.
</Callout>

</Phase>

The processor fetches the post caption, then calls Gemini with a structured

Gemini answers live comments with `503` when it is busy, so `429`s, `5xx`s
and timeouts go back to SQS with a delay of 1 minute, 10 minutes, then 1
hour, and only a fourth failure is stored. Any other failure, like an
expired token, is stored as an `error` row straight away, since retrying it
just burns invocations. `scripts/reprocess_events.py` re-drives those by
error code once the cause is fixed.

<Phase
  id="metrics-poller"
  title="Metrics poller"
  status="done"
  goal="Collect post, follower and account insights durably, often enough to measure a fresh Reel by the hour, without paying to keep a database awake."
  outcome="One five-minute tick polls whatever is due; an idle tick costs one DynamoDB read and no database work."
>

There is one EventBridge rule and no tiers. Each tick asks every subject
whether it is overdue, using fetch clocks stored on the rows themselves, so
a missed tick heals itself.

| What | Interval |
|---|---|
| Media list (new post?) | 15 min |
| Follower count | 5 min while a post is under 24h old, else 30 min |
| Post insights | 5 min under 6h, then 15 min, 1h, 6h up to a month, then daily |
| Account insights + daily roll-up | 24h |

The first thing a tick does is read one DynamoDB item holding the earliest
moment anything is due. Most ticks stop there (~130 ms). Due times for
anything polled every 15 minutes or less snap to a shared wall-clock grid,
so jobs batch onto the same ticks: a simulated quiet day reaches the
database 96 times, evenly spaced, instead of ~200. Dense samples go to
DynamoDB, which has no idle charge, and Postgres is written once a day.

<Callout variant="warning" title="Meta's reporting day is not a UTC day">
  Account insights come back with `end_time` at `07:00:00+0000`, labelled by
  the day the window started. Filing them under UTC dates shifted every
  point by a day. Account rows are now filed under Meta's reporting day, two
  days back so Meta has finished counting.
</Callout>

<Phase
  id="instagram-proxy"
  title="Token ownership and proxy"
  status="done"
  goal="Take the long-lived Instagram token off the tablet, without breaking the tablet's comment logic or letting a read-only client moderate."
  outcome="The token lives only in AWS; clients moderate comments and answer DMs through seven scoped proxy routes."
>

The poller is the only identity with `PutSecretValue`, and refreshes the
token when fewer than 10 days remain. The token is read at runtime and never
cached across invocations. A CloudWatch alarm on `TokenDaysRemaining` treats
missing data as breaching, so a poller that stops running also sends an
email. It is the one alarm kept, because it is the one failure a redeploy
cannot fix.

- **Lease, not reserved concurrency.** The account's Lambda quota is 10, and
  AWS refuses any reservation below that floor, so exclusivity comes from a
  conditional DynamoDB write that expires on its own.
- **Meta's JSON passes through unchanged.** The tablet's comment threading
  handles several undocumented Meta behaviors, and reshaping the payload
  would have meant porting all of it during a cutover.
- **JWT scopes.** The write routes need `instagram:write`. Tokens minted
  before scopes existed still read everything and are refused only on
  writes: a missing claim grants nothing.
- **History import.** `scripts/import_tablet_history.py` loads the tablet's
  daily snapshots tagged `source = 'tablet'`, and a real poll always wins
  over an imported row for the same day.

</Phase>

<Phase
  id="analytics-api"
  title="Analytics API"
  status="done"
  goal="Answer questions the tablet never could, once metrics and comment analyses sit in the same database."
  outcome="Posting slots, time to 80% reach, per-post daily gain and comment quality, each one API route."
>

The routes are shaped around resources, not screens, so a UI change never
needs a backend change. Derived numbers are computed on the server so the
tablet and the dashboard cannot drift apart.

- `/metrics/timing` requires an explicit IANA `tz`. Buckets built on UTC
  hours would answer "best time to post" for the wrong country.
- `/metrics/velocity` reads the dense samples and returns `null` unless
  sampling started before the post reached 80%, so it measures the post and
  not when polling began.
- `/metrics/media-daily` resolves `audience` per post (views for a Reel,
  reach for a feed post), because asking for either column drops the other
  kind of post without an error.
- `/metrics/comment-quality` returns a `coverage` block saying how many
  analyses could be joined to a post, instead of quietly under-counting.

<Phase
  id="dm-conversations"
  title="DM conversations"
  status="done"
  goal="Give DMs the same review-then-act loop as comments, where the thing to judge is a whole conversation rather than one message."
  outcome="Each incoming message re-analyses its conversation, and any outgoing message closes it."
>

Every incoming message re-reads its whole conversation under prompt `dm-v1`
and writes a new `conversation_analyses` row: an English summary, tags, a
suggested action, and a reply drafted in the customer's language.

- **What closes it:** an outgoing message, sent from the Instagram app or
  through the API, is recorded as the reply that answers the conversation.
- **Acting on it:** two more proxy routes send a DM and heart a message,
  under the same `instagram:write` scope as comment moderation.
- **History:** a throttled backfill script analyses conversations that
  arrived before this existed.

<Phase
  id="comment-tags"
  title="Comment tags and post ideas"
  status="done"
  goal="Group comments by what they are, so the account can see what people ask for and turn it into the next posts."
  outcome="Six fixed tags replace a free-text topic that gave 134 distinct topics for 178 comments."
>

The prompt asks for one tag per comment from a list the account owner
chose: question, dish request, tried it, criticism, compliment or other. It
comes from the same Gemini call, through a schema where it is required, and
the draft follows a rule per tag:

- **Question:** answer from the caption, without inventing quantities it
  does not give.
- **Tried it:** thank them and invite a photo.
- **Criticism:** stay factual.
- **Compliment:** one line.

<Screenshot
  src="/images/projects/instagram-dashboard/topics.webp"
  alt="Six tags with a bar each, from 31 questions down to 3 other, each with how many were replied to and how many are open"
  caption="/metrics/tags rendered by the dashboard: comments per tag, with how many got a reply and how many are still open. Fictional data."
/>

`POST .../content-ideas` hands Gemini the recent questions, dish requests,
criticism and tried-it comments, as English summaries with their captions
and never their authors, and returns 3-5 post ideas, each citing the
comments it answers. An idea that cites no real comment is dropped, and
nothing is stored.

<Callout variant="decision" title="Re-running history must not disturb what reads it">
  Re-analysing old comments under a new prompt cannot bring handled ones
  back. The listing shows each comment's newest successful analysis, so a
  failed re-run keeps the old one. An action belongs to the comment, not to
  an analysis row. Quality, sentiment and coverage count each comment once.
</Callout>

</Phase>

<Phase
  id="dsql-migration"
  title="Moving to Aurora DSQL"
  status="done"
  goal="Stop paying ~$57 a month for a Postgres that never got to pause, without rewriting a repository or losing a row in the move."
  outcome="Aurora DSQL behind the existing Data API seam: ~40k DPU a month, inside the free tier, and 0 when idle."
>

A spike against a DSQL cluster loaded with a copy of production data
measured ~40k DPU a month for the same traffic, against a free tier of 100k.
The move was a run of small changes, each deployable on its own:

1. **An adapter**, `db/dsql.py`, that speaks the RDS Data API's
   `execute_statement` shape over an IAM-authenticated psycopg connection,
   so every repository ran unchanged.
2. **DSQL next to Aurora**, with a $5 monthly budget counted before
   credits, since DSQL has no capacity cap to stop a runaway bill.
3. **A baseline schema** in DSQL's dialect, and a copy script that compares
   an md5 over every table. Rehearsed on production data: migrated in 25 s,
   all 10 tables byte-identical.
4. **The switch**, then the Aurora cluster and its code path removed.

| DSQL behaviour | How the adapter handles it |
|---|---|
| Closes connections at 60 min, and frozen Lambdas wake with dead sockets | Recycle a connection past 50 min of age or 4 min idle |
| Optimistic concurrency, so conflicts surface as `40001` | Retry with backoff; retry a dropped connection for reads only, never writes |
| An open transaction is billed | Autocommit on every connection, matching the Data API |

<Callout variant="lesson" title="Scale-to-zero needs gaps longer than the pause timeout">
  Aurora pauses only after 300 seconds with no query. About 30 subjects
  kept their own polling clocks, so some tick did a small job every 5-10
  minutes, and the cluster sat at its 0.5 ACU floor 80-85% of every quiet
  day: ~$57 a month instead of the expected $4-6. Few queries is not enough;
  the quiet stretches have to outlast the timeout, or the database has to
  bill per request instead.
</Callout>

</Phase>

<Phase
  id="query-api-cold-start"
  title="Query API cold starts"
  status="done"
  goal="Cut what the dashboard waits for when the query API starts cold, since it sits behind every page load."
  outcome="Imports drop from 756 to 286 ms with precompiled bytecode, and the API gets its own 1024 MB setting."
>

| Change | Effect |
|---|---|
| Precompiled bytecode in every package | `query_api` imports from 756 to 286 ms, measured locally on Python 3.12 |
| Query API memory from 256 to 1024 MB | A cold container took ~2.2 s to start, then ~3.8 s more opening the DSQL connection; CPU scales with memory |

The bytecode fix is the same read-only `/var/task` trap the
[dashboard's backend](/projects/instagram-dashboard/#page-load) hit: the
package script deleted every `__pycache__` and never compiled any. The
webhook, processor and poller stay at 256 MB, and all of it stays inside the
free tier at this traffic.

</Phase>

<Phase
  id="media-kit"
  title="Media kit"
  status="done"
  goal="Answer what a brand asks before a collaboration (reach, engagement, audience, best Reels) with figures that match Instagram's own app, without spending the Graph rate limit on every request."
  outcome="A daily stored media kit that matches Instagram's app: views within 0.1%, reach within 0.9%."
>

The daily roll-up builds the kit and stores it whole, one row per day.
`GET /accounts/{id}/media-kit` reads that row and never calls Graph, so
asking for it costs no rate limit, and a figure quoted to a brand can be
rebuilt from the day it was taken.

| Section | What it holds |
|---|---|
| `performance` | Meta's own 30-day totals: accounts reached and engaged, views, interactions, likes, comments, saves, shares, and engagement rate (interactions over reach) |
| `audience` | Followers by age, gender and country, unknown gender kept in. Meta's breakdowns of the reached and engaged accounts come back empty |
| `top_reels` | The ten Reels with the most lifetime views, with a current thumbnail added when served, since a stored CDN link expires within days |
| `account` | Followers now and at the window's start, and the first post's date |

- **Its own token.** Tied to one account, 90 days by default, refused on
  every other route. Its key is derived from the shared secret and a
  generation number, so bumping the number revokes every media-kit token
  without logging out the dashboard or the tablet.
- **Rate-limited at API Gateway**, so a flood is turned away before it
  takes the Lambda concurrency the webhook needs.

<Callout variant="lesson" title="Unique counts do not add up">
  A daily reach row counts each account once that day, so thirty of them
  added up count a returning viewer up to thirty times: about a fifth above
  Instagram's own figure for the same window. Asked for over the whole
  window instead, reach lands within 0.9% of the app, and views,
  interactions and accounts engaged within 0.1%.
</Callout>

</Phase>

<Phase
  id="media-kit-mcp"
  title="Media kit over MCP"
  status="done"
  goal="Let someone ask Claude or ChatGPT about the account's reach and audience in a chat, with the model reading the real figures rather than guessing, and reaching nothing but the media kit."
  outcome="Claude and ChatGPT read the media kit through one read-only MCP tool, with a token scoped to it alone."
>

`POST /mcp` serves one tool, `get_media_kit(as_of?, top_reels?)`. It takes
media-kit tokens only, and the account comes from the token's own claim, so
nothing the model sends can name another one.

The `401` names the protected resource metadata (RFC 9728), which names
the [dashboard's backend](/projects/instagram-dashboard/#ai-app-sign-in) as
the authorization server. Once the person allows the app, that backend asks
the agent to mint an ordinary media-kit token, passing the authorization
code's id as a single-use key: a conditional DynamoDB write, so a code
mints one token, ever.

The tool's description tells the model how to read the figures, since it
will quote them to someone:

- reach counts each account once across the window;
- the audience is followers, not the accounts reached;
- gender `U` is unknown, so "% women" without it is a different figure;
- a `null` means Meta did not report it, never zero.

## Future improvements

- **Liking comments.** It needs `graph.facebook.com` and Facebook Login for
