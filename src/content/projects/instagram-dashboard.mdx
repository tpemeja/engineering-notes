## Overview

<Screenshot
  src="/images/projects/instagram-dashboard/insights.webp"
  alt="Dashboard Insights page under the six-tab navigation, with a followers card, a posts tracked card, 7/30/90 day toggles and a follower growth chart"
  caption="The Insights page. The freshness line says which half of the page is sealed daily history and which half is live. All screenshots use a fictional account."
/>

A website for checking my wife's Instagram account from anywhere, built on
top of the [Instagram Agent](/projects/instagram-agent/). The
[tablet](/projects/instagram-insight/) is great for a glance at home, but it is
stuck on a wall. This is the same data on a phone or a laptop, with more room
for tables and for handling comments and DMs.

It has six pages: Insights, Posts, Trends, Comments, Topics and Events. A
reply, hide, delete or DM goes through the agent, and lands in the same
action table the tablet reads. A weekly digest email sums up the week, and a
[public demo](https://dashboard-demo.kaseovo.com) runs the same frontend on a
made-up cooking account.

## Problem

- **The API token is not scoped per account.** Any valid management token
  can read any account, so it must never reach a browser where devtools
  could pull it out.
- **The site is on the public internet.** It has to be reachable from
  anywhere, but stay private to a few invited people, with no account system
  to build or run.
- **Two clients, one to-do list, and a third that keeps no record.** A
  comment answered on the tablet must not still show as "to handle" on the
  website, and a reply written in the Instagram app records nothing at all.
- **The data has holes that look like zeros.** Collection started at
  different times for different metrics, and daily history is only sealed
  two days late.
- **The AWS account allows 10 concurrent Lambdas.** Each dashboard call uses
  two (this backend plus the agent), the Insights page asks for nine things
  at once, and any of them can land on a cold start.

## Approach

The browser gets nothing it could leak. The backend holds every secret, the
frontend holds a session cookie, and each route is a straight pass-through
to the agent scoped to one account ID. Query params and response shapes are
forwarded unchanged, so the agent stays the only place where a metric is
defined. The public demo follows the same rule from the other side: it has
no backend at all, so there is nothing in it to leak.

The UI is honest about what it does not know. A `null` from the agent is
rendered as a dash and sorted last, a window that covered fewer days than it
names gets a marker, and the Insights page and the digest both state how
fresh each half of their data is.

The backend runs Google's authorization-code flow itself, with PKCE and a
`state` cookie, so the browser only ever follows redirects and the client
secret never leaves the server. Rotating the session key logs every session
out, which is the point of rotating it.

<Callout variant="lesson" title="A page load can throttle your own backend">
  Nine requests at once meant ~18 concurrent Lambdas against a limit of 10.
  The overflow came back as `503 Service Unavailable` from API Gateway, which
  CloudWatch shows as throttles with zero errors, because nothing crashed.
  Every request now goes through one client-side gate of three in flight,
  which leaves room for the poller, webhook and processor that share the
  limit.
</Callout>

Post insights are lifetime counters that only climb, so the raw total says
how big a post is, not whether anyone is still watching it. The table ranks
on the day-over-day gain the agent computes instead.

<Screenshot
  src="/images/projects/instagram-dashboard/trends.webp"

- **Today** is only answerable for posts sampled more than once a day, and
  is counted from the local midnight, not UTC.
- **A window ends at a missing day** instead of being voided, so one gap
  does not blank a whole column.

<Phase
  id="comment-handling"
  title="Comment handling"
  status="done"
  goal="Review the agent's analysis of each new comment and act on it from any device, without the website and the tablet disagreeing about what is left to do."
  outcome="Reply, hide, delete or acknowledge from the browser, and the tablet's to-do list clears too."
>

Comments opens on **To handle**: analyses with no recorded action, grouped
by post, with a filter row to work through one tag at a time. Each row shows
the AI's suggested action, sentiment, reply score and summary. Reply opens
the draft for editing, and every write asks for confirmation.

<Screenshot
  src="/images/projects/instagram-dashboard/to-handle.webp"
  alt="A French question tagged Question with its suggested reply open in an editable box, an English translation of the draft underneath, and a Publish reply button"
  caption="To handle: the AI suggests, a person edits and publishes. A draft in another language shows its English translation underneath. Fictional account and comments."
/>

The translation runs once when the box opens and is cached by draft text.
After an edit it marks itself out of date and offers to redo it, rather than
spending the Gemini quota comment analysis needs on every keystroke.

Actions follow the tablet's write-then-report order: the Instagram write
goes through the agent's proxy first, and only a confirmed result is
recorded.

| Failure | What happened | Retry |
|---|---|---|
| Instagram failure | Nothing changed on Instagram | Safe to retry the whole action |
| Recording failure | Instagram succeeded, the record did not | Retry only the recording, never the post |

The list re-syncs every 30 seconds and when the tab regains focus, without
dropping comments loaded with "Load more" or a reply being typed.

</Phase>

<Phase
  id="direct-messages"
  title="Direct messages"
  status="done"
  goal="Answer DMs from the same To handle list as comments, inside the 24-hour window Instagram allows for a reply."
  outcome="DMs read as conversations and can be answered or liked until Instagram's 24-hour window closes."

Events shows each conversation as one chat-style card. To handle gets a
Direct messages section fed by the agent's conversation analyses: tags, an
English summary, the thread, and the actions below. Past the 24-hour window,
only the last one is offered.

- **Reply** sends the DM, with the same English translation under the draft.
- **Like** hearts the message.
- **Acknowledge** or **Already done on Instagram** records it without
  sending anything.

<Callout variant="lesson" title="A timestamp without a zone is local time to the browser">
  The agent sends analysis times as `2026-09-29 22:38:23`: UTC, with no
  zone. `new Date` reads that as local time, so in Tokyo every card showed
  nine hours early, and the 24-hour window could be reported closed while it
  was still open. One shared parser now pins the bare form to UTC and leaves
  timestamps that carry an offset alone.
</Callout>

</Phase>

<Phase
  id="reply-status"
  title="Replies made in the Instagram app"
  status="done"
  goal="Stop comments answered in the Instagram app from sitting in To handle forever, since a reply written there never reaches the action table."
  outcome="Comments answered in the app show as Replied or Probably replied, read from the thread itself."

The thread is the evidence. To handle reads the stored comments from the
oldest pending one onwards (usually one request, nothing asked of
Instagram), and tags each comment by what the account wrote after it.

| What the thread shows | Tag | Effect |
|---|---|---|
| The account's reply @mentions the commenter, or they are the only other person in the thread | Replied | Sure; flagged in To handle |
| The account only wrote later in the same thread | Probably replied | Dashed tag; never suppresses the suggested reply |

<Phase
  id="page-load"
  title="Faster first load"
  status="done"
  goal="Open the dashboard after a break without waiting 8-10 seconds on Lambda cold starts stacked one behind the other."
  outcome="Panels draw as their data lands, and cold-start imports drop from 518 to 222 ms with precompiled bytecode."
>

Almost all of the wait was cold starts queued behind each other. Five
changes cut it down, at no added cost:

| Change | What it saves |
|---|---|
| No session check before a page loads; the first 401 from a data route sends you to sign-in | A full round trip, usually a cold start |
| Insights draws each panel as its data arrives, requesting in page order | The top of the page fills first instead of waiting on all nine |
| One HTTP client per process instead of one per call | A new connection to the agent on every call |
| Lambda memory from 256 to 1024 MB, still inside the free tier | CPU scales with memory; a cold start spent ~1.8 s on imports and the secret fetch |
| Precompiled bytecode in the package | Imports from 518 to 222 ms, measured locally on Python 3.12 |

<Callout variant="lesson" title="A read-only filesystem cannot cache bytecode">
  The package script removed every `__pycache__` and never compiled any, and
  `/var/task` is read-only, so each cold start compiled FastAPI and pydantic
  from source and could not keep the result. The bytecode is now compiled by
  the same Python version as the runtime, in unchecked-hash mode, so the
  zip's file times cannot invalidate it.
</Callout>

</Phase>

  id="topics"

The agent's analysis gives each comment one of six tags: question, dish
request, tried it, criticism, compliment or other. Topics counts them, then
breaks the busiest posts down by tag; a click on a post's segment opens
those comments. The same tags and colours drive the filter row in To handle.

<Phase
  id="weekly-digest"
  title="Weekly digest email"
  status="done"
  goal="Bring the week to people who will not open the dashboard: the numbers, what is waiting, the posts that did best, what people talked about and ideas for the next posts."
  outcome="An email every Sunday at 20:00 Tokyo time, sent only to people who subscribed and verified themselves."
>

<Screenshot
  src="/images/projects/instagram-dashboard/digest.webp"
  alt="Top of the digest email: follower, views, reach and interactions tiles with week-on-week changes, a Needs you card with comments and DMs waiting, and the most watched posts with their pictures"
  caption="The top of a digest, rendered by the real template on a made-up week. Account insights cover the newest seven days Meta has sealed; followers are live, and the email says so."
/>

- **Its own Lambda and IAM role**, built from the backend's package, fired
  by EventBridge Scheduler and sent through SES. The API Lambda never holds
  permission to send email.
- **A section that fails is reported in the email**, not dropped. Silence
  on a Sunday looks exactly like a quiet week.
- **Post pictures travel inside the message** as `cid:` attachments,
  because Instagram's thumbnail links expire within days and an email is
  read whenever it is read.
- **Each person subscribes themselves** on the Digest page, as the Google
  account they signed in with. A subscriber is a tagged SES identity, so the
  verification link SES sends is the confirmation.

<Callout variant="lesson" title="A test that skips the preflight tests nothing a browser does">
  Unsubscribe sends a `DELETE`, and CORS only allowed `GET` and `POST`, so
  every browser's preflight was refused and the button failed for everyone.
  The route's tests sent the `DELETE` straight to it, skipping the
  preflight, and passed. A test now asks the way a browser does.
</Callout>

</Phase>

<Screenshot

  alt="Pink demo banner explaining it is a made-up cooking account with nothing connected to Instagram, with a Start over link, above the dashboard's six-tab navigation"

A demo build answers every request in the browser, from an invented cooking
account laid out around the moment the page opens: the newest post is always
a few hours old, and a few comments and a DM arrive while it is open. What a
visitor does stays in their own localStorage and resets at their midnight.
The switch is a build-time constant, so the normal build drops the demo code
entirely.

What keeps it harmless even if its code changes:

- **No backend, no shared state.** A Cloudflare Worker serves static files,
  so nothing one visitor types can reach another.
- **`connect-src 'self'`** in its Content-Security-Policy makes the browser
  refuse any request off the demo's own origin, the real API included.
- **The real session cookie is host-only** on the API's subdomain, and the
  API's CORS and Origin checks accept only the real dashboard.
- **The Cloudflare token** belongs to a `demo` environment that only `main`
  may deploy to, and only the deploy step sees it.

## Future improvements

- **No roles, and no names on actions.** Everyone on the invited list can do
  everything, and the action table does not record who handled a comment.
- **The digest is still in SES's sandbox.** Every subscriber has to verify
  their address first, and the list is capped at 10.
- **Concurrency is capped client-side.** The real fix is raising the AWS
  Lambda quota, which is a support request rather than a code change.
